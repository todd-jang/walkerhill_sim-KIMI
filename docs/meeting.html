1. 왜 이 회의가 필요한가

초안 v2의 L2 문턱 "공유 태그 2개 이상"은 태그 어휘가 미정의라 A의 임의 태그 부여 시 설계자 재량에 좌우되고, C의 미선택 사유 기록·D의 설명력 평가가 어휘 불일치로 분석 불가가 된다. 해결: 원본 상태기계 문서에서 SKU에 이미 붙어 있는 속성 축을 태그 어휘로 채택 — 임의 발명이 아닌 기존 enum 재사용으로 검증 가능하게 한다.

2. 태그 축 5개 (원본 문서 근거)

축 이름 값 예시 원본 출처
① 업장 타입 뷔페 / 정찬코스 / 라운지 / 바 / 델리 / 테이크아웃 / 인룸다이닝 (7종) §3.2 업장 타입별 state
② 가격 밴드 조식 8.5만 / 코스 12.5~19.5만 / 뷔페 17.6~19.8만 / PDR 창가 5만 부가 §4 업장별 가격표 (◎ 공식)
③ 끼니 슬롯 조식 / 중식 / 석식 / 티타임(브런치 10-14) / 해피아워 / 야식(BAR 20:00-01:00) §3.2 라운지 state + §4 운영 시간
④ 구역 그랜드 / 비스타 / 더글라스 / 야외(리버파크) §8.2 노드 그룹 (대괄호 그룹핑이 이미 구역)

핵심 원칙: 태그는 임의로 붙이지 않는다. 위 5축의 enum 값만 사용한다.

3. L2 채택 규칙 (수정안)

3.1 공식 정의

공유 태그 = 5축의 속성 값 일치. "① 업장타입 + (②③④⑤ 중 1개 이상)" 을 공유할 때 L2 유추 채택.

3.2 왜 "2개 이상"이 아니라 "①+1개"인가

  • ①은 필수 — 같은 업장 타입이어야 "업장에서의 행동 경험"이라는 맥락이 유지된다. 델리 경험을 정찬에 옮겨 쓰는 것은 L2 취지와 맞지 않는다.
  • ①외 축은 전이 방향을 결정한다:
공유 축 전이되는 것 예시
② 가격 밴드 가격 민감도 뷔페 17.6만 부담 → 정찬 16.5만 부담
③ 끼니 슬롯 시간대 선호 조식 선호 경향 → 타 업장 조식
④ 구역 동선 (보조 지표로만) §8.4가 전부 △ 추정치이므로 동선은 주 근거로 쓰지 않음
⑤ 이용 조건 조건 수용 2인 조건 수용 → PDR 조건 수용

3.3 L2 유추 강도 세분화 (선택)

등급 조건
L2-α (강한 유추) ① + 3개 이상 공유
L2-β (기본 유추) ① + 1~2개 공유

4. 원본 값으로 본 채택 예시

출처 근거 (L1) 대상 SKU 공유 축 결과 판정
"더뷔페 석식 19.8만 부담" 온달 수라상차림 19.5만 ② 가격밴드(17~20만) + ③ 석식 고가 석식 기피 ✅ 채택
"더뷔페 석식 부담" 온달 낮것상 12.5만 (주중 점심) 가격 구간 다름, 슬롯 다름 — ❌ 불가
"피자힐만 별로였다" 온달 출처 한정 서술 — ❌ 불가 (규칙 2.3-b)
"르 파사쥬 포장이 좋았다" 피자힐 착석 ① 델리 vs 정찬 — 타입 불일치 — ❌ 불가
"모에기 2인 조건 불편" 명월관 별채 (최소 2일 전 예약) ⑤ 이용조건 + ① 정찬 사전 조건 민감 ✅ 조걶부 — 원문에서 인원/기간 구분 필요

5. 인터페이스 합의 안건

5.1 C에게 — 미선택 사유 기록 4축과 5축 매핑

C 기록 축 (초안 v2 §4.2) 대응 태그 축 처리
가격 ② 가격 밴드 그대로 대응
시간 ③ 끼니 슬롯 그대로 대응
동선 ④ 구역 그대로 대응 (단 §8.4 △ 추정치이므로 보조 지표로만)
취향 (원본 문서에 없음) 페르소나 쪽 dining_pref.csv 어휘 유지 — 원본 enum이 아니므로 L2 공유 태그로는 쓰지 않음

합의 요청: C의 미선택 사유 4축과 위 매핑이 일치하는지 확인. 취향 축만 별도 어휘임을 명시.

5.2 D 팀장에게 — 설명력 평가 기준 반영 여부

  • L2-α/β 강도 차이를 "뒷받침 인정" 기준에 반영할지?
  • ⑤ 이용 조건 축은 개인 성향이 아니라 상황 조건에 가까움 (가격·취향과 성격이 다름) — L2 공유 태그에 포함할지, 아니면 4축(①~④)으로 좁힐지 판단 요청

5.3 A팀 남은 작업

  • SKU 178개에 5축 태그 일괄 부여 — §4 가격표 + §4 백틱 헤더에서 자동 추출 가능분 먼저 처리
  • 태그 부여 후 L2 후보 연결 자동 생성 → L2-α/β로 분류
  • 결과를 D 팀장에게 전달해 설명력 평가 입력으로 활용

6. 시뮬레이션 검증 결과 (2026-11-14 실측)

§4 문서 파싱 → 5축 태그 부여 → L2 연결을 실제로 실행해 본 결과, 태그 체계의 구조적 결함이 확인됐다. 이것이 이 회의의 추가 안건이다.

6.1 실측 수치

단계 결과
SKU 추출 169개 · 업장 7개 (목표 178개에 근접 — 차이는 §4.9~4.13 가격 미공개 업장 = §10 미확보 데이터)
타 업장 L2 후보 쌍 3,599개 → 출처당 대표 3개 선별 시 404쌍
α/β 분포 L2-α 263개 / L2-β 141개

6.2 확인된 결함 2가지

결함 1 — 음식↔주류가 같은 후보로 묶임

가격밴드가 같다는 이유만으로 사케와 한우가 "대체 가능한 상품"으로 연결된다. 이것은 연구질문 2의 "상식적인 대체 패턴" 요건에 위배된다.

결함 2 — L2-α가 너무 쉽게 달성됨

"①업장타입 + 3축 공유" 조건이지만, 실제로는 가격밴드·끼니슬롯·구역만 맞아도 α가 된다. 결과적으로 α 263개 대부분이 이 조합 — 강도 구분이 실질적으로 무의미하다.

6.3 구조적 원인과 제안

문제 원인 제안
음식↔주류 혼합 메뉴 카테고리 축 부재 — 현재 5축에 "코스/일품/주류/디저트" 구분이 없음 6번째 축 "메뉴 카테고리" 추가
α 남발 가격·슬롯·구역은 같은 타입 업장끼리 거의 자동 공유 α 조건 강화: 카테고리 동일 + 가격밴드 + 1축 이상

6.4 이것이 회의 안건인 이유

태그 축 추가는 A 단독 결정이 아니다: - C의 미선택 사유 기록도 카테고리 구분이 필요할 수 있음 (예: "주류 미선택" vs "일품 미선택"은 다른 분석) - D의 설명력 평가에서 "사케 인용 Fact가 한우 선택을 뒷받침한다"는 판정이 가능한지 기준 필요 - ⑤ 이용 조건 축 포함 여부(§5.2)와 같은 성격의 결정 — 5축/6축 체계 자체를 합의로 확정해야 함

v3 스크립트(카테고리 필터 적용)는 작성 완료. 합의 후 실행 예정.
